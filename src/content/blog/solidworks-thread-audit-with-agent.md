最近在做 SolidWorks 自动审核工作流时，我先选了一个范围很小但很具体的问题：**能不能自动发现零件版本之间的螺纹错漏？**

相比“让 AI 自动设计一个零件”，这个问题更适合作为工程自动化的起点，因为输入和输出都比较明确：给定两个 SolidWorks 零件版本，读取特征树，识别螺纹相关特征，比较规格和数量，最后把差异整理成工程师可以复核的结果。

## 1. 为什么先做螺纹检查

在真实 CAD 文件里，螺纹并不只是一个名字。SolidWorks 中可能通过 Hole Wizard、Cosmetic Thread 等不同特征表达，因此如果只比较文件名、尺寸文本或者截图，很容易漏掉真正的模型语义。

我最终采用的路线是直接通过 SolidWorks COM 打开零件，然后遍历 Feature Tree，重点识别：

- `HoleWzd`：标准孔向导 / 螺纹孔相关特征；
- `CosmeticThread`：装饰螺纹特征；
- 特征名称中的 M4、M6、M8 等规格。

这样做的目标不是“让 LLM 猜螺纹”，而是先把 CAD 里的确定性信息提取出来，再让上层工作流做组织、比较和解释。

## 2. 最小工作流

这条审核链可以概括成：

```text
输入两个零件版本
        ↓
SolidWorks COM 打开模型
        ↓
遍历 Feature Tree
        ↓
提取 HoleWzd / CosmeticThread / 规格
        ↓
生成结构化特征清单
        ↓
版本差异比较
        ↓
输出 CSV / Markdown / JSON
        ↓
工程师复核
```

这里最重要的一点是：**自动化负责把“哪里不同”完整地找出来，工程师负责判断“这个不同是不是设计错误”。**

## 3. 实际验证结果

我用两个实际零件版本进行对比，一个是“有螺牙”版本，一个是“无螺牙”版本。

最终得到的统计结果如下：

| 项目 | 有螺牙版本 | 无螺牙版本 |
| --- | ---: | ---: |
| 特征树总数 | 72 | 48 |
| 螺纹相关特征总数 | 26 | 11 |
| HoleWzd 数量 | 6 | 3 |
| CosmeticThread 数量 | 20 | 8 |
| M8 螺纹孔 | 1 | 0 |
| M6 螺纹孔 | 3 | 1 |
| M4 螺纹孔 | 2 | 2 |

其中最明确的一条异常是：**无螺牙版本缺失 M8 螺纹孔。**

除此之外，还能看到 HoleWzd 和 CosmeticThread 的数量差异，因此最终输出不会只给一个“PASS / FAIL”，而是保留完整特征差异，方便人工判断。

## 4. 为什么不能直接把“差异”写成“错误”

这是我做这类工程自动化时越来越在意的一点。

工具可以告诉我：

- 某个版本少了一个 M8 Hole Wizard；
- 两个版本的 CosmeticThread 数量不同；
- 某些组件对出现静态干涉候选。

但这些信息本身并不能自动证明设计错误。

例如一个干涉候选可能是正常配合关系，某个螺纹差异也可能来自版本目的不同。因此工作流里必须保留人工确认边界。

我更愿意把这类系统理解为 **engineering evidence generator**：自动收集、整理、定位工程证据，而不是替工程师做最终设计放行。

## 5. 从脚本到 MCP / Worker

最初这个检查只是本地 Python + COM 脚本。之后为了让 Agent 可以稳定调用，我把它继续封装进 MCP + Worker 工作流。

整体结构大致是：

```text
Codex / Agent
      ↓
MCP Tool
      ↓
Worker
      ↓
SolidWorks COM
      ↓
审核结果
```

Worker 的存在主要是为了处理 SolidWorks 这类长时间、依赖图形会话的任务。Agent 不需要一直阻塞等待，而是提交任务、获得 `job_id`，再查询状态和最终结果。

当前这条链路已经可以通过 MCP 提交审核任务，并返回螺纹差异、静态干涉候选以及结果文件路径。

## 6. 安全与运行边界

这类 CAD 自动化不能只考虑“能不能跑”，还要限制它能做什么。

当前我保留了几个边界：

- MCP 不暴露任意命令执行能力；
- 输入模型来自受控目录；
- 审核对象使用复制后的 CAD 模型；
- 不覆盖原始 CAD 文件；
- 任务成功只代表脚本和证据产出成功，不代表设计放行。

这些限制让工作流更接近“可审查的工程自动化”，而不是一个拥有无限权限的 Agent。

## 7. 开源仓库给了什么，项目侧又补了什么

这个过程里我也调研并验证过 `solidworks-automation-skill` 开源仓库。它提供了 SolidWorks COM 连接、文档打开、特征树遍历、基础导出等能力，适合作为自动化底座。

但实际验证时也遇到一些问题，例如部分示例导入路径和真实模块不一致、中文 SolidWorks 环境下英文草图名选择容易失败、`hole_wizard()` 仍是空框架等。

因此我逐渐形成一个判断：**通用开源库适合解决“怎么连上 SolidWorks”，但真实工程规则、审核逻辑、结果证据和人工门禁仍然需要项目侧自己沉淀。**

## 8. 下一步

螺纹检查目前只是一个比较窄的审核切口。后面我想继续做几件事：

1. 扩展到装配体全量扫描，而不是只比较单个零件；
2. 建立允许差异、标准件、允许配合的规则库；
3. 把异常位置投影到工程图视图中，生成更直观的复核标记；
4. 把审核任务纳入统一队列，支持更完整的失败恢复和状态追踪。

真正有意思的问题并不是“AI 能不能控制 SolidWorks”，而是：**怎样让 Agent 在复杂工程软件里获得足够可靠、可解释、可追溯的状态和证据。**
